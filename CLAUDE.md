# CLAUDE.md — working agreement for the Quran Knowledge Graph

This repository builds a Curiosity application for **studying the Quran as a knowledge graph,
Arabic first**. Read [README.md](README.md) and [docs/use-case.md](docs/use-case.md) first; the
repository layout and commands are in [AGENTS.md](AGENTS.md). The skills in `.claude/skills/`
are the reference for each layer — `quran-data` for this corpus, the `curiosity-*` ones for the
platform.

Five layers, in dependency order — a layer may only depend on one above it:

| # | Layer | Where | Skill |
|---|---|---|---|
| 1 | The corpus | `data/manifest.json`, `src/QuranKG.Dataset` | `quran-data` |
| 2 | The graph connector | `src/QuranKG.Connector` | `curiosity-data-connector`, `curiosity-graph-modelling` |
| 3 | The workspace configuration | `src/QuranKG.Definitions/config` | `curiosity-workspace-configuration` |
| 4 | Endpoints and the AI layer | `src/QuranKG.Definitions/code` | `curiosity-code-endpoints`, `curiosity-similarity-scenarios`, `curiosity-ai-tools-and-agents` |
| 5 | The front end | `src/QuranKG.FrontEnd` | `curiosity-frontend-setup`, `curiosity-node-renderers`, `curiosity-dashboards-and-lists` |

## Non-negotiables

1. **Arabic first.** Search, similarity and clustering read the Arabic (`Verse.TextSimple` for
   models, the morphology's roots and lemmas for the graph signals). Translations are reading aids
   and never a signal. Quranic text is displayed through `Components/Arabic.cs` (RTL, Amiri).
2. **The answer keys stay out of the AI's reach.** QurSim (`QurSimPair`) is how similarity and
   themes are scored, the ruku' (`Verse.Ruku`, `Surah.RukuCount`) how passages are, and the QUL
   topics will score clusters too. No similarity signal, clustering run, AI tool, index the AI can
   query, prompt or sandbox may read them. `qkg/verse/words` returns QurSim pairs for people — it
   must never become an AI tool.
3. **Never write a node type, field or edge as a string literal.** Use `N.<Type>.<Field>` /
   `E.<Edge>` — generated by `just emit-schema` for the front end, injected by the workspace into
   endpoints. A literal fails silently; a constant fails the build.
4. **Everything crossing the wire is a `UID128`**, and every count ships the UID of what it
   counted, so a chart row opens its node.
5. **Every metric is computed live from the graph.** Nothing pre-aggregated, nothing hard-coded
   (not even "6,236" in UI text — read it from the response).
6. **`AddOrUpdate` writes a node's whole content**: one write per node per run, carrying all its
   fields.
7. **Every node type has a renderer** (`src/QuranKG.FrontEnd/src/Renderers`).
8. **The workspace lives in git.** After any change in the admin UI: `just export-definitions`,
   diff `.export/` against `src/QuranKG.Definitions/`, commit what you mean to keep. A new
   machine is rebuilt from this repository with `just bootstrap`.
9. **Every definition file opens with its attribute header** (`[endpoint: …]` on the first lines,
   comments below). The DTO library `code/endpoints/qkg/_lib/dto.cs` must never contain the
   literal import directive in a comment: the importer matches it anywhere and the library would
   import itself.
10. **The DTOs are declared twice and generated once**: edit `_lib/dto.cs`, then `just sync-dto`
    rewrites `src/QuranKG.FrontEnd/src/Api/Dto.cs` (`--check` fails on drift).

## Order of a change

```
corpus change        → QuranKG.Dataset (+ tests) → `just check-data`
schema change        → Connector Schema.cs/Edges.cs → `just ingest` → `just emit-schema`
                       → re-export config/schemas → endpoints → front end
endpoint change      → code/endpoints → (DTO? `just sync-dto`) → `just upload-endpoints`
front-end change     → `dotnet build src/QuranKG.FrontEnd` → `just upload-frontend`
clusters change      → try it in tools/cluster-benchmark (`just benchmark-clusters --split dev`)
                       → qkg/clusters/build.cs → `just upload-endpoints` → `just clusters`
after any ingest     → `just clusters` (the build reads the graph; the connector never writes clusters)
```

Import definitions **after** an ingest has created the schema: an endpoint naming a type the
graph does not have does not compile.

## Validation gates

```bash
just test                       # corpus tests — must pass
just check-data                 # the corpus loads and adds up
just ingest local --dry-run     # mapping counters, nothing written
dotnet build QuranKG.slnx       # everything compiles (the front end needs `tps`)
dotnet run --project src/QuranKG.Tools -- sync-dto --check
just status                     # after an import: "Code compiles", counts as expected
```

## Gotchas learned building it

- Endpoint answers are cached (`CacheFor(3600)`) **per user**, keyed on the endpoint's own code:
  a change to `_lib/dto.cs` alone does not invalidate its dependents — restart the workspace.
- Only one embeddings index per field: `Graph.Embeddings.GetIndex` returns the first. Switch with
  `just embeddings-arabic` / `-ollama` / `-harrier`, which delete before they create.
- The verses' Arabic is embedded by AraModernBert-STS through `tools/embedding-server`: it must be
  running (`just up` starts it) for the workspace to embed a verse or answer a semantic search.
- Embeddings index `MinimumLength` defaults to 20 characters, which skips short verses (الم):
  ours are 1.
- Exact similarity search: hand `FindSimilar` fewer than 1,000 candidate UIDs at a time (the HNSW
  walk misses neighbours); `qkg/verse/similar` batches 900.
- Never run the workspace with `MSK_LOW_MEMORY`: six times slower on the dashboard endpoint.
- The endpoints that read the clusters are NOT cached: with `CacheFor(3600)` a rebuild showed the
  previous build for an hour. They answer in under a second; keep it that way.
- `ReadOnlyNode` is a class: `FirstOrDefault()` over nodes gives null, not an empty node.
- Session tokens do not survive a workspace restart; the minted Library / Upload tokens do.
- In an AI tool, `scope.RunEndpointAsync<string>` returns **null** for an endpoint that answers
  with a DTO (it converts only a string): read it as `RunEndpointAsync<JObject>` / `<JToken>`.
- The stock chat page starts every chat with only consult ticked, whatever the assistant pins:
  the tools reach the model because `Chat/QuranChatView.cs` pins them on post and replace.
- Clusters have three kinds: Passage and Theme (`qkg/clusters/build`), SimilarGroup
  (`qkg/clusters/similar-build`). A build deletes only its own kinds; a reader filters on Kind (a
  passage's `InTheme` is its theme; its similarity group is found from the group's `HasPassage`).
- Endpoints can be written in the workspace too (Sudo wrote the similarity groups there):
  `just export-definitions` and diff before `just upload-endpoints`, which overwrites what it uploads.
- In the front end, no CSS class may contain `ec-`: the icon font's rule `span[class*="ec-"]` sets
  such a span in monospace (`qkg-sec-head` did; the reader's classes are `qkg-pas-…`).
- Arabic in Amiri Quran has a line box about twice the letters' height: mark words with a colour,
  not a background, or the marks become tall blocks.
- The chat's `CustomMessageRenderer` receives each message before its markdown is drawn, and a
  reply only once streaming ends (the transcript is reloaded): to rewrite a message's text, watch
  it with a `MutationObserver` (`Components/VerseReferences.cs`), do not read it once.
- The sandbox has no `query` command on purpose: the query engine emits whole nodes, and a verse
  node carries its ruku'.

## Commits

- Branch per piece of work; never push to `main` directly. Do not open a PR unless asked.
- Commit in logical chunks; never commit `data/raw/`, `.env`, `.workspace/`, `.export/`, build
  output or benchmark output (`tools/embedding-benchmark/out`, `.venv`).
- Keep [TODO.md](TODO.md) current: every gap found gets an item; tick it off in the commit that
  closes it.
